## 1. 지금 상황 정리

이번이 이 3개 화면(+ 랭킹)에 대한 첫 시도가 아닙니다.

- **6/30** `20260630_design_proposal.md` — 라이트 테마 전면 리디자인 제안. 이 문서에도 이미 "모든 수치는 fig 원본(프레임 기준 **834×1194px, iPad 세로**)에서 추출"이라고 명시돼 있지만, 반응형 처리는 "실제 앱은 가변폭이니 **max-width 480~560px**(모바일) 컨테이너에 중앙 정렬하고 비율을 clamp()로 환산"하는 쪽으로 결론이 났습니다. 즉 834px는 "수치를 뽑아온 원본 캔버스"였을 뿐, **실제 상한으로 쓰지는 않았습니다.**
- **9/3** `20260903_figma_sync.md` — 지금과 거의 동일한 요청("figma에 그려진 각 화면이 비율상 최대 크기라 봐주면 될 것 같아. 반응형 디자인은 유지해주면 좋을 것 같아")을 홈/캐릭터 선택/팀 참여/랭킹 4개 화면에 대해 이미 하셨고, 지금 코드는 그 결과물로 보입니다.

그래서 지금 코드(`LandingPage`, `TeamCodeInput`, `CharacterSelect`)는 이미 Figma와 구조·색상·폰트가 상당히 가깝습니다. Figma 변수(`Blue/100 #1051c2`, `Black/100 #111111`, `Black/80 #888888` 등)와 코드의 `--blue-100`, `--ink`, `--ink-2` 토큰이 정확히 일치하고, 홈 화면 타이틀의 `clamp(36px, 8.6vw, 72px)` 도 최댓값이 Figma 실측치(72px / weight 900 / letter-spacing -1.8px)와 정확히 같습니다. **"완전히 다시 만들어야 하는" 상태는 아닙니다.**

그런데도 "완전히 동일하게 만들기 어렵다"고 느끼신 이유는, 코드를 직접 뜯어보니 두 가지 구조적인 문제 때문으로 보입니다.

### 1.1 문제 ① — 화면 틀(#root) 자체의 비율이 Figma와 다름

`src/index.css`에서 앱 전체를 담는 `#root`는 뷰포트 폭에 따라 3단계로 비율이 바뀝니다.

| 구간 | 현재 비율(가로:세로) | Figma 원본 비율 |
|---|---|---|
| ~767px (모바일) | `390 : 844` ≈ 0.462 | — |
| 768~1023px | `820 : 1040` ≈ 0.788 (근사치) | — |
| 1024px~ | `1100 : 1100` = 1.0 (정사각형에 가까움) | — |
| **Figma 프레임** | — | **`834 : 1194` ≈ 0.698 (아이패드 세로)** |

즉 지금은 좁은 화면에서는 세로로 긴 폰 모양, 넓은 화면에서는 거의 정사각형으로 바뀌는데, **Figma는 모든 경우에 항상 0.698 비율(아이패드 세로)**입니다. 어느 구간에서도 `#root`의 비율이 Figma와 정확히 맞아떨어지는 지점이 없습니다. 각 화면(`LandingPage.module.css` 등)에서 `clamp()`와 `%` 패딩으로 최대한 맞춰보려 하지만, 틀 자체의 비율이 다르니 "거의 비슷하지만 완전히 같지는 않은" 상태가 될 수밖에 없습니다.

### 1.2 문제 ② — 요소별 축소 비율이 제각각이라, 화면이 작아질수록 Figma와 벌어짐

개별 `clamp()` 값들의 **최댓값은 Figma와 정확히 일치**하지만, 화면이 좁아질 때 얼마나 빨리 줄어드는지(`vw` 계수)는 요소마다 따로 정해져 있습니다.

```css
/* LandingPage.module.css 발췌 */
.iconBox { width: clamp(90px, 18.7vw, 156px); }   /* 18.7vw로 축소 */
.title   { font-size: clamp(36px, 8.6vw, 72px); } /* 8.6vw로 축소 */
.primaryBtn { font-size: clamp(19px, 3.1vw, 26px); } /* 3.1vw로 축소 */
```

각 요소가 서로 다른 속도로 줄어들기 때문에, 뷰포트가 딱 834×1194일 때는 Figma와 같아 보여도, 그보다 작은 임의의 크기(예: 태블릿 가로 모드, 좁은 창)에서는 아이콘·글자·버튼의 **상대적 비율이 Figma와 어긋납니다.** "링크를 줘도 완전히 똑같이 안 나온다"는 체감은 대부분 이 지점에서 나옵니다.

## 2. 요청하신 규칙을 구현 규칙으로 번역하면

> "Figma 화면이 최대 크기다. 그보다 화면이 커지면 Figma와 동일하게 나온다. 화면이 작아지면 아이콘·이미지 크기가 비례해서 줄어든다."

이걸 CSS로 옮기면 다음 두 문장이 됩니다.

1. **상한**: 화면(정확히는 화면을 담는 컨테이너)이 `834×1194px` 이상으로 커질 수 있어도, 콘텐츠 프레임은 `834×1194px`에서 성장을 멈춘다. 그 이상은 프레임 바깥 여백(지금처럼 카드가 가운데 떠 있는 형태)으로 처리한다.
2. **하한 쪽 축소**: `834×1194px`보다 작은 화면에서는, 프레임 안의 **모든 요소(폰트·아이콘·여백·모서리 반경 등)가 정확히 같은 비율로 함께 줄어든다.** 특정 요소만 더 빨리/느리게 줄어들지 않는다 — 즉 Figma 프레임을 그대로 축소 복사한 것처럼 보여야 한다.

2번이 지금 코드와 가장 다른 지점입니다. 지금은 "요소마다 적당히 비슷하게 줄어드는" 방식이고, 요청하신 건 "전체가 하나의 배율로 함께 줄어드는" 방식입니다.

## 3. 구현 방식 2안 비교

### 안 A — 통일된 스케일 변수 (`--vscale`) 방식 · **추천**

페이지(또는 `#root`) 최상단에서 "지금 화면이 Figma 대비 몇 %냐"를 나타내는 스케일 값 하나를 계산해두고, 모든 크기 값을 `Figma 실측값 × 스케일`로 통일합니다.

```css
.gridWrapper {
  container-type: size; /* 이미 CharacterSelect.module.css에 적용돼 있는 패턴 */
}
:root, [data-figma-frame] {
  /* 컨테이너 크기를 834×1194 기준 비율로 환산해 1을 넘지 않게 클램프 */
  --vscale: clamp(0.55, min(100cqw / 834, 100cqh / 1194), 1);
}

.title { font-size: calc(72px * var(--vscale)); }      /* Figma 실측값 × 배율 */
.iconBox { width: calc(156px * var(--vscale)); }
.primaryBtn { height: calc(68px * var(--vscale)); font-size: calc(26px * var(--vscale)); }
```

- **장점**: 이미 `CharacterSelect.module.css`에서 쓰고 있는 `container-type: size` + `cqw` 패턴을 그대로 확장하는 것이라 팀 컨벤션과 맞습니다. 순수 CSS만으로 동작하고(추가 JS 불필요), 모든 요소가 정확히 같은 비율로 줄어들어 Figma를 그대로 축소한 것처럼 보입니다. 특정 구간(예: 캐릭터 그리드가 정사각형 4×4 → 가로로 넓게 펼쳐지는 것처럼)에서는 지금처럼 레이아웃 자체를 바꾸는 것도 그대로 병행할 수 있습니다.
- **단점**: 화면마다 Figma 실측값을 하나하나 `calc(px × var(--vscale))` 형태로 다시 옮겨 적어야 해서, 화면당 작업량이 (지금의 `clamp()` 방식보다) 조금 더 듭니다. 다만 이번에 이미 Figma 변수/치수를 다 확인해뒀기 때문에 3개 화면 정도면 부담스러운 양은 아닙니다.

### 안 B — 프레임 전체 `transform: scale()` 방식

`834×1194px` 고정 크기로 페이지를 그대로 만들고(Figma 좌표를 거의 그대로 px로 옮김), 화면이 그보다 작을 때만 `transform: scale(비율)`로 프레임 전체를 축소합니다.

- **장점**: "Figma와 완전히 동일"이라는 보장이 가장 강합니다(좌표를 그대로 옮기고 통째로 축소하는 것이므로). 화면별 변환 공식을 일일이 손으로 옮길 필요가 없습니다.
- **단점**: 프레임 내부에서 반응형으로 "재배치"하는 게 사실상 불가능해집니다(전체가 하나의 딱딱한 판처럼 통째로 축소·확대만 됨). 매우 넓거나 좁은 화면비에서는 프레임 주변에 빈 여백이 많이 남습니다. 입력창·버튼 같은 실제 클릭/터치 영역도 시각적으로만 작아지는 게 아니라 실제 히트박스까지 작아져, 아주 작은 화면에서 터치 조작성이 떨어질 수 있습니다.

**추천: 안 A.** 지금 코드베이스가 이미 이 방향으로 절반쯤 가 있고(`container-type`, `cqw`, Figma 변수 이름을 맞춰둔 spacing 토큰 주석 등), 앞으로 다른 화면(로비, 랭킹 등)에도 같은 패턴을 계속 재사용할 수 있습니다. 안 B는 "일단 눈으로 완전히 똑같은지부터 빨리 보고 싶다"는 경우의 임시 검증 수단으로는 유용할 수 있어, 화면별 작업 중 최종 확인 단계에서 잠깐 활용하는 정도로 제안합니다.

## 4. 화면별 확인 결과

세 화면 모두 Figma 프레임 크기는 동일하게 **834×1194px**였습니다.

### 4.1 홈 화면 (node 1757:169)

구조(로고 박스 → 타이틀 → 서브타이틀 → 버튼 2개 → 푸터, 우상단 관전자/관리자 버튼)가 `LandingPage.jsx`와 그대로 일치합니다. 색상·타이포 토큰도 일치 확인.

- ⚠️ Figma 프레임에는 CTA가 **"시작하기" / "랭킹 보기" 2개**만 보이는데, 현재 코드에는 밑줄 텍스트 버튼 "우리 아이 경제 잠재력 테스트"(퀴즈 진입)가 하나 더 있습니다. 유지할지 삭제할지 확인 필요 (6.3 참고).

### 4.2 팀 참여 화면 (node 1558:2031, "팀 참여")

뒤로가기 + 타이틀 "팀 참여" + 서브타이틀 + 카드(라벨 "초대 코드" + 입력창 + "팀 참여하기" 버튼) 구조가 `TeamCodeInput.jsx`와 일치합니다.

- ⚠️ 이 노드는 초대 코드 입력 화면 하나뿐입니다. 지금 프로젝트에는 같은 템플릿을 쓰는 **"이름 입력"(`NameInput.jsx`, `/join` 경로) 화면이 별도로 존재**하는데, 이번에 주신 링크에는 포함돼 있지 않습니다. 요청하신 제목이 "이름 입력 및 팀 참여 화면"이라 두 화면을 함께 가리키시는 건지, 이번엔 팀 참여만 먼저 하는 건지 확인이 필요합니다 (6.4 참고).
- Figma의 카드 컴포넌트 이름이 `GlassCard`/`GlassInput`인데, 스크린샷상으로는 반투명·블러 효과 없이 흰 배경 + 파란 테두리로 보입니다(지금 코드와 동일한 느낌). 실제 유리(glass) 효과를 의도하신 건지, 그냥 컴포넌트 이름일 뿐인지 실제 작업 단계에서 Dev Mode 수치로 한 번 더 확인하겠습니다.

### 4.3 캐릭터 선택 화면 (node 1558:1947)

헤더 + 구분선 + 4×4 캐릭터 그리드 + 하단 CTA 구조가 `CharacterSelect.jsx` / `CharacterCard.jsx`와 일치하고, **캐릭터 일러스트 16종(`public/characters/*.png`)도 이미 Figma 그리드와 동일한 동물 구성으로 전부 준비돼 있습니다.** 이 화면은 에셋 관점에서는 추가 작업이 필요 없고, 반응형 규칙만 맞추면 됩니다. 참고로 그리드 영역은 이미 `container-type: size` + `container query`로 "좁으면 정사각형 4×4, 620px 이상이면 가로로 펼침" 전환이 구현돼 있어, 안 A(§3)와 가장 궁합이 좋은 화면입니다.

## 5. 작업 순서 제안

말씀하신 대로 화면 단위로 순서대로 진행하되, 네 화면이 모두 같은 `#root` 틀을 공유하므로 **공통 토대를 먼저 한 번 손보고 그 다음 화면별로 세부 조정**하는 순서를 제안합니다. (아래 0단계는 완료됐고, 1~4단계는 §8에 구체 규격까지 정리해뒀지만 코드에는 아직 적용 전입니다.)

1. **0단계 — 이 제안서 확정**: ~~아래 6번 질문에 답변.~~ → 완료 (§6 참고).
2. **1단계 — 공통 인프라**: `index.css`의 `#root` 규칙을 834×1194 상한 + `--vscale` 방식으로 교체. (한 번만 하면 이후 화면 작업이 훨씬 단순해짐) → 규격 확정, 코드 미적용.
3. **2단계 — 홈 화면**: `LandingPage` 조정 → 834×1194에서 Figma와 픽셀 단위로 비교 → 임의로 좁힌 화면(예: 375px, 700px)에서 비율이 유지되는지 확인 → 승인 후 다음 단계. → 규격 확정(§8.2), 코드 미적용.
4. **3단계 — 팀 참여 + 이름 입력 화면**: `TeamCodeInput`과 `NameInput`(같은 템플릿 재사용) 동일한 방식으로 조정·검증. → 미착수.
5. **4단계 — 캐릭터 선택 화면**: `CharacterSelect`/`CharacterCard` 조정·검증. 그리드 전환 구간(620px)이 `--vscale` 방식과 충돌하지 않는지 함께 확인. → 미착수.

각 단계마다 Figma 스크린샷과 실제 구현 화면을 나란히 놓고 확인한 뒤 다음 화면으로 넘어가는 방식으로 진행하겠습니다.

## 6. 결정 사항 (2026-09-07 확정)

1. **상한 적용 범위** → 전역이 아니라 **이번 4개 화면(홈 · 이름 입력 · 팀 코드 입력 · 캐릭터 선택)에만** 적용. 로비/팀 현황/랭킹 등 아직 Figma 동기화가 안 된 다른 화면은 지금의 `#root` 규칙(390:844 폰 비율 + 768px/1024px 근사 확장)을 그대로 유지.
2. **"최대 크기"의 의미** → **절대 상한.** `834×1194px`를 넘지 않는다. 처음엔 "비율(0.698)만 유지하고 그 이상은 자유롭게 커져도 된다"는 쪽으로 시도해보셨는데, 그렇게 하니 padding·이미지 크기 등이 의도한 디자인과 너무 달라지는 걸 확인하셨습니다 — Figma가 실제로 그 크기까지만 디자인됐기 때문에, 그보다 큰 화면에서 같은 비율로 계속 키우면 애초에 검증되지 않은 크기의 UI가 나오는 게 당연한 결과입니다. §3에서 추천한 안 A가 원래부터 이 절대 상한 방식이었으므로 그대로 유지합니다.
3. **홈 화면의 퀴즈 링크** → 이번 작업 범위에서 **제외**. 손대지 않고 지금 있는 그대로 둡니다.
4. **"이름 입력" 화면 포함 여부** → **포함, 총 4개 화면.** 단 이름 입력(`NameInput.jsx`, `/join` 경로) 전용 Figma 프레임은 없고, 지금 코드처럼 **팀 참여(`TeamCodeInput`) 화면과 같은 템플릿을 재사용**하기로 함(두 화면이 이미 `NameInput.module.css` 하나를 공유 중이라 코드 구조와도 맞음). 그래서 팀 참여 화면 스펙을 정하면 이름 입력 화면도 라벨/문구만 다르게 자동으로 따라갑니다.
5. **축소 하한선** → **현재와 동일.** `--app-min-height: 600px`, `--app-max-width: 430px` 등 지금 `index.css`에 있는 최소 크기 값을 그대로 가져갑니다. 새로 낮추거나 높이지 않음.

## 8. 확정된 구현 규격 (다음 작업 시 이 스펙대로 적용)

결정이 끝났으니, 실제로 코드에 옮길 때 그대로 쓸 수 있게 규격을 구체적으로 적어둡니다. **아래 내용은 설계만 끝난 상태이고, 현재 저장소 코드에는 반영돼 있지 않습니다.**

### 8.1 공통 인프라 — `src/index.css`

기존 `body.quiz-mode` / `body.admin-mode`와 같은 패턴으로, 이번 4개 화면 전용 `body.onboarding-mode`를 추가합니다. 각 페이지 컴포넌트에서는 이미 있는 `useBodyClass` 훅(`src/hooks/useBodyClass.js`, `QuizIntro.jsx`가 `useBodyClass('quiz-mode')`로 쓰는 것과 동일한 훅)을 그대로 재사용해 `useBodyClass('onboarding-mode')`만 호출하면 됩니다.

```css
/* 온보딩 화면(홈 · 이름 입력 · 팀 참여 · 캐릭터 선택) 전용 모드.
   Figma 시안 그대로인 834×1194(아이패드 세로)를 절대 상한으로 삼는다:
   화면이 그보다 커져도 프레임은 834×1194에서 성장을 멈추고(카드처럼 가운데 뜬 채
   유지), 그보다 작아지면 비율을 유지한 채 프레임 전체가 함께 줄어든다.
   768px/1024px 구간의 근사 오버라이드와 480px 이하의 풀블리드 오버라이드는
   width/height/aspect-ratio/border-radius/box-shadow를 다시 선언해 여기서 무효화한다
   (선택자 특이도 body.onboarding-mode #root > #root 이므로 항상 우선 적용됨).
   #root에 container-type: size를 둬서, 각 화면의 CSS가
   `calc(<Figma 실측 px> * var(--vscale))` 형태로 크기를 계산할 수 있게 한다
   (--vscale은 각 페이지의 .page 루트에서 `calc(100cqw / 834)`로 정의). */
body.onboarding-mode #root {
  width: min(100%, calc(100dvh * (834 / 1194)), 834px);
  height: auto;
  aspect-ratio: 834 / 1194;
  max-width: 834px;
  max-height: 1194px;
  min-height: var(--app-min-height); /* 결정 5: 기존 최소 크기 그대로 */
  border-radius: 28px;
  box-shadow:
    0 30px 90px rgba(70, 79, 144, 0.26),
    0 10px 28px rgba(17, 24, 39, 0.10);
  container-type: size;
}
```

`:root`에는 Figma 변수 컬렉션의 `shadow` 값(`#BEDBFF80` 2겹 그림자)을 그대로 옮긴 토큰을 하나 추가해, 로고 박스·주요 버튼에서 재사용합니다.

```css
--shadow-blue: 0 2px 4px -2px rgba(190,219,255,.502), 0 4px 6px -1px rgba(190,219,255,.502);
```

각 페이지 컴포넌트에서:

```jsx
import useBodyClass from '../hooks/useBodyClass'
// ...
useBodyClass('onboarding-mode')
```

그리고 각 페이지의 `.page` 클래스 최상단에:

```css
.page {
  --vscale: calc(100cqw / 834);
  /* 이하 모든 크기는 calc(<Figma 실측 px> * var(--vscale)) 형태로 작성 */
}
```

### 8.2 홈 화면(LandingPage) 상세 스펙 — 다른 화면 작업 시의 예시 템플릿

Figma 실측치를 다시 확인하는 과정에서, 현재 코드와 아래처럼 구체적인 차이를 발견했습니다(다음 작업 때 함께 반영):

| 항목 | 현재 코드 | Figma 실측 | 비고 |
|---|---|---|---|
| 우상단 버튼 그룹 오른쪽 여백 | 24px | **32px** | `834 - (608+193.99998)` |
| 로고/타이틀 블록 ↔ 버튼 블록 간격 | 40px | **48px** | `652 - (308+296)` |
| "시작하기"(primary) 버튼 높이 | 68px | **76px** | |
| "랭킹 보기"(secondary) 버튼 높이 | 68px | **80px** | Figma에서 두 버튼 높이가 서로 다름 |
| 로고 박스 · 버튼 그림자 | 근사 rgba 값 | **`--shadow-blue` 토큰** | Figma `shadow` 변수 그대로 |
| 푸터 위치 | `position:absolute; bottom:24px`로 하단 고정 | **버튼 블록 뒤에 자연스럽게 흐르는 요소(간격 46px)** | 캔버스 하단의 넓은 여백은 `.page`의 `justify-content:center`가 자동으로 만들어줌 |
| 타이틀/서브타이틀/버튼 텍스트 `line-height` | 브라우저 기본값 | Figma 실측 비율(타이틀 1, 서브타이틀 1.4, 버튼 1.08, 상단 버튼 1.27, 푸터 1.33) | 폰트 크기 대비 줄간격까지 일치시킴 |
| 퀴즈 링크 버튼("우리 아이 경제 잠재력 테스트") | — | 이번 범위 제외, 기존 값 그대로 유지 |

나머지 값(타이포 크기, 색상, 아이콘 비율 64%/70% 등)은 이미 Figma와 정확히 일치해 그대로 가져가면 됩니다. 팀 참여/이름 입력, 캐릭터 선택 화면도 실제 작업 시 이와 같은 방식(메타데이터 실측 → 현재 코드와 대조 → 차이 표로 정리 → `--vscale` 기반으로 이식)으로 진행하면 됩니다.
