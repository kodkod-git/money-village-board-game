### 테스터 제약 (결과 해석 시 참고)

- **이번 세션은 예정보다 크게 축소되었다.** 최초 시도는 백그라운드 서브에이전트(fork)로 전체 3.1/3.2/3.3/4장 회귀 전수 점검 + 신규 연결 끊김 검증을 병행하려 했으나, 해당 fork가 관찰 가능한 진행(브라우저 탭 생성, 서버 요청, 리포트 파일) 없이 10분 이상 멈춰 있어 중단하고 이 세션에서 직접 브라우저를 조작했다. 이후 턴 예산 문제로 **3.1/3.2/3.3 전수 회귀는 생략**하고, 사용자가 이번 세션에서 명시적으로 요청한 **연결 끊김 관련 신규 검증(5장)에 집중**했다. 기존 체크리스트는 아래 2·3장에 "Skip(경량 확인만)"으로 표시했다.
- `mcp__claude-in-chrome__computer`의 `ref` 기반 클릭이 이 앱의 React 컴포넌트(특히 커스텀 `role="button"` 카드, CSS-module 버튼)에서 신뢰성 있게 동작하지 않아 — 클릭이 기록되지만 React 상태가 갱신되지 않는 현상 반복 — 이후 `javascript_tool`의 `element.click()` 직접 호출로 전환했다. 또한 `computer` `screenshot` 액션이 반복적으로 30초 타임아웃되어(이전 리포트 ISSUE-6과 동일 계열 증상, 이번엔 `/admin`에서도 발생) 이번 세션 내내 스크린샷 대신 `get_page_text`/`read_page`/직접 fetch로 상태를 확인했다. 두 현상 모두 자동화 툴링 환경 이슈로 추정되며 앱 자체의 결함으로 보진 않는다.
- 한글 IME 대신 라틴 문자 이름(Player1~4)을 사용했다(이전 세션과 동일한 제약).

### 5.3 시나리오 B-2 — 플레이어가 직접 나갔을 때(자진 퇴장) 등록 가능 여부 — ⚠️ 버그 발견

**절차**: 새 팀 2(934D47)에 Player3(자산 입력 완료)·Player4(미완료) 참가 → Player4 탭에서 "뒤로" → 커스텀 확인 모달 "방 나가기" → "나가기" 클릭.

| 확인 항목 | 결과 | 근거 |
|---|---|---|
| UI상 정상 흐름(확인 모달 → 캐릭터 선택 화면으로 이동) | Pass | 클라이언트 라우팅은 정상 동작, 네이티브 dialog 아님 |
| **팀원 목록에서 Player4가 실시간으로 사라짐** | **Fail** | 남은 Player3 탭에서 `GET /api/rooms/934D47` 재조회 시에도 Player4가 여전히 `players` 배열에 남아있음(`connected: true`, `isCompleted: false`) — 두 번 재확인해도 동일 |
| 관리자 화면에서도 동일하게 확인 | **Fail(재현)** | 관리자 탭에서 같은 API를 직접 조회해도 Player4가 그대로 남아 있음. 즉 "나가기"를 눌러도 **서버 쪽 방 상태에서 플레이어가 전혀 제거되지 않는다** |
| 결과 등록 가능 여부 | 간접 Fail | Player4가 여전히 방에 남아 있고 `isCompleted: false`이므로, 팀은 "미입력자 있음" 사유로 계속 등록이 막힌다(연결 끊김 차단이 아니라 "완료 안 됨" 차단이지만, 근본 원인은 나가기가 작동하지 않았기 때문) |

**결론 및 근본 원인 (메인 세션에서 재현 + WebSocket 프레임 캡처로 확정)**: "플레이어가 직접 나갔을 때 결과 등록이 되는지"에 대한 답은 **현재 구현에서는 "아니오"**. fork가 원인 불명으로 남긴 부분을 이어서, `WebSocket.prototype.send`를 몽키패치해 실제 소켓 프레임을 캡처한 결과 근본 원인을 특정했다:

```
"42[\"leave-room\"]"
"42[\"join-room\",{\"code\":\"781539\",\"name\":\"Player1\",...,\"playerUuid\":\"318c237b-...\"}]"
```

`leave-room`은 서버에 정상 도달하고 `removePlayer`도 정상 동작한다(`room.players`에서 즉시 제거됨). **문제는 서버가 `removePlayer`에서 해당 소켓을 Socket.IO room 채널에서 `socket.leave(code)`로 내보내지 않는다는 점**(`server/rooms.js` `removePlayer`, `server/index.js:523-541` `leave-room` 핸들러 어디에도 `socket.leave()` 호출 없음). 그 결과 이미 나간 플레이어의 소켓이 여전히 `io.to(room.code).emit('room-updated', ...)` 브로드캐스트를 수신하며, 이 이벤트가 아직 언마운트되지 않은(라우팅 전환 중인) `Team.jsx`의 `players` state를 갱신한다. 이로 인해 `src/pages/Team.jsx:42-59`의 자동 재접속 effect(`if (players.find(p => p.socketId === socket.id)) return` → 없으면 `join-room` 재전송, 원래는 연결 끊김 후 재접속 시나리오를 위한 로직)가 "나는 방에 없다 = 재접속해야 한다"로 오판해 **즉시 `join-room`을 재전송, 방금 나간 플레이어를 그대로 재참가시켜 버린다**. 실제로 `GET /api/rooms/:code` 재조회 시 나간 플레이어가 `connected:true` 상태로 그대로 남아있음을 확인했다(재현 2/2, fork 세션 1회 + 메인 세션 1회 독립 재현).

**관리자 강퇴(B-1)는 왜 우연히 정상으로 보였는가**: B-1에서 kick 대상은 이미 소켓 연결이 끊긴(`connected:false`) 상태였다 — 죽은 소켓은 애초에 어떤 브로드캐스트도 수신할 수 없으므로 이 재참가 버그가 드러나지 않았을 뿐이다. **아직 연결된(정상 접속 중) 플레이어를 관리자가 강퇴하는 경우까지 확인하니, 관리자 강퇴 경로(REST `DELETE /api/admin/rooms/:code/players/:playerUuid`, `AdminSpectateModal`이 호출)에도 동일한 원인의 버그가 있었다** — `leave-room` 소켓 핸들러와 마찬가지로 대상 소켓을 Socket.IO room에서 내보내지 않아, 연결된 상태로 강퇴당한 플레이어도 이론상 동일하게 재참가할 수 있었다(자진 퇴장과 달리 `you-were-kicked` 안내 모달이 `room-updated`보다 먼저 처리되어 화면이 곧장 전환되는 경우가 많아 실제 발현 빈도는 낮았을 것으로 추정되나, 근본 원인은 동일).

### ✅ 수정 완료 (같은 세션에서 적용 및 재검증)

두 지점 모두 대상 소켓을 `room.code` Socket.IO room에서 명시적으로 `leave()`시키도록 수정했다:
- `server/index.js` `socket.on('leave-room', ...)` — `removePlayer` 직전 `socket.leave(roomBefore.code)` 추가.
- `server/index.js` `DELETE /api/admin/rooms/:code/players/:playerUuid` — `io.sockets.sockets.get(targetSocketId)?.leave(room.code)` 추가.

**재검증 결과**:
| 시나리오 | 수정 전 | 수정 후 |
|---|---|---|
| 자진 퇴장(2인 방, WebSocket 프레임 캡처) | `leave-room` 직후 `join-room` 재전송 확인(버그) | `leave-room`만 전송, 재조인 없음. 남은 팀원 화면에 실시간으로 반영됨 |
| 관리자가 **연결된** 플레이어 REST로 강퇴(신규 테스트, 이전 세션엔 없던 케이스) | (미검증 상태였음 — 이번에 처음 확인, 동일 버그 존재) | 재조인 없이 정상 제거, "팀에서 나가게 되었어요 / 방장이 팀에서 내보냈어요" 안내 모달 정상 표시 |
| `npx vitest run` (전체 563개) | — | 수정 전/후 모두 563 passed — 회귀 없음 |

수정 후에는 B-1(강퇴)과 B-2(자진 퇴장) 모두 "결과 등록" 차단이 정상적으로 풀린다 — 애초에 두 경로 모두 플레이어가 방에서 확실히 사라지므로, 5.1의 연결 끊김 차단 로직과는 무관하게 정상 진행된다.

### ISSUE-A — "방 나가기(나가기)" 직후 클라이언트가 자기 자신을 즉시 재참가시킴 (심각도: 높음, ✅ 같은 세션에서 수정 완료)

| 항목 | 내용 |
|---|---|
| 역할 | 학생 |
| 화면/기능 | 팀 화면(`/team/:code`) "뒤로" → "방 나가기" 확인 모달 → "나가기" |
| 재현 경로 | 팀에 참가 → 팀 화면에서 "뒤로" 클릭 → 모달에서 "나가기" 클릭 |
| 기대 동작 | 해당 플레이어가 `room.players`에서 즉시 제거되고, 남은 팀원 화면에 실시간 반영 |
| 실제 동작 | `leave-room`은 서버에 정상 도달해 `removePlayer`로 즉시 제거되지만, 서버가 해당 소켓을 Socket.IO room에서 `leave()`시키지 않아 나간 소켓이 곧이은 `room-updated` 브로드캐스트를 계속 수신한다. 이 이벤트가 아직 언마운트 전인 `Team.jsx`의 자동 재접속 effect를 트리거해 **`join-room`을 즉시 재전송, 방금 나간 플레이어를 그대로 재참가시킨다**. WebSocket 프레임 캡처로 `leave-room` 직후 `join-room`이 같은 플레이어로 재전송되는 것을 확인(`server/rooms.test.js` 등 서버 단위 테스트만으로는 이 클라이언트-서버 상호작용 버그가 드러나지 않음) |
| 코드 위치 | 서버(1차 원인): `server/index.js:523-541`(`socket.on('leave-room', ...)`)가 `removePlayer` 후 `socket.leave(room.code)`를 호출하지 않음 / 클라이언트(2차, 방아쇠): `src/pages/Team.jsx:42-59`(자동 재조인 effect)가 "나는 방 목록에 없다"를 무조건 재접속 신호로 해석 |
| 적용한 수정 | 서버 `leave-room` 핸들러와 `DELETE /api/admin/rooms/:code/players/:playerUuid`(관리자 강퇴) 양쪽에 대상 소켓을 `socket.leave(room.code)`로 Socket.IO room에서도 제거하는 코드를 추가. 같은 세션에서 적용 후 WebSocket 프레임 재캡처 + UI 확인으로 재검증 완료(아래 "수정 완료" 참고) |
| 부가 영향 | 이 버그로 인해 "연결 끊긴 플레이어가 스스로 나갔을 때 등록이 풀리는지"(이번 세션 핵심 요청 중 하나)를 처음엔 검증할 수 없었으나, 수정 후 재검증하여 정상 동작 확인. 재현율(수정 전): fork 세션 1회 + 메인 세션에서 WebSocket 프레임 캡처로 독립 재현 1회, 총 2/2 |

### 관찰 사항 (이슈는 아니나 참고)

- `mcp__claude-in-chrome__computer`의 `ref` 클릭이 이 앱의 커스텀 `role="button"` 카드/CSS-module 버튼에서 신뢰성이 낮음(React 상태 미반영) — 자동화 툴링 이슈로 추정, 앱 버그 아님.
- `/admin` 등 여러 화면에서 `computer` `screenshot` 액션이 반복적으로 30초 타임아웃 — 이전 리포트 ISSUE-6("lobby 렌더러 응답 지연")과 유사 계열. 이번엔 `/lobby`가 아닌 `/admin`에서도 발생해 특정 라우트 문제라기보다 툴/환경 전반 이슈일 가능성이 높다.

## 7. 총평

**이번 세션의 핵심 요청(연결 끊김 시 등록 차단 검증)은 명확한 결과를 얻었다**:

1. **연결 끊김 상태의 결과 등록 차단(시나리오 A)** — 개별 등록·일괄 등록 모두 설계 문서(`2026-08-24-block-registration-disconnected-design.md`)와 정확히 일치하게 동작한다. **정상.**
2. **관리자 강퇴 후 등록(시나리오 B-1)** — 정상 동작, 연결이 끊긴(stale) 플레이어도 문제없이 퇴장 처리되고 이후 등록이 성공한다. **정상.**
3. **플레이어 자진 퇴장 후 등록(시나리오 B-2)** — **버그 발견 → 같은 세션에서 수정 완료(ISSUE-A)**: "나가기"를 눌러도 클라이언트가 즉시 자기 자신을 재참가시켜 실질적으로 나가지지 않는 버그였다. 근본 원인(서버가 나간/강퇴된 소켓을 Socket.IO room에서 `leave()`시키지 않아 계속 `room-updated`를 수신하고, 클라이언트의 "연결 끊김 후 재접속" 로직이 이를 오해석)을 특정해 수정했고, 같은 버그가 **관리자가 연결된 플레이어를 강퇴하는 경로**(이전 세션엔 없던, 이번에 새로 발견한 케이스)에도 있었다는 것까지 확인해 함께 수정했다. 수정 후 두 경로(자진 퇴장 / 관리자 강퇴) 모두 재검증 통과, 전체 테스트(563개) 회귀 없음.

3.1~3.3의 전수 회귀 체크리스트는 턴 예산 제약으로 이번 세션에서 생략했다(경량 확인만 수행, 확인된 항목은 모두 이전 수정 사항이 유지되고 있음을 재확인함). 다음 세션에서 시간이 확보되면 전수 회귀를 우선 진행할 것을 권장한다. ISSUE-A는 이번 세션에서 원인 특정 및 수정까지 완료되어 더 이상 후속 조치가 필요하지 않다.

리포트 파일과 QA 시뮬레이션 제안서(`proposal/20260918_qa_simulation_proposal.md`, `proposal/20260831_qa_simulation_proposal.md`)는 함께 보관해 다음 테스트 세션에서 회귀 여부를 비교할 수 있게 한다.
